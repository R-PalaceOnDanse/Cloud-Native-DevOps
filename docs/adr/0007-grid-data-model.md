# ADR-0007 — Grid data model: Firestore pixels with Cloud Storage tiles

- **Status**: Accepted
- **Date**: 2026-10-22
- **Deciders**: project owner; team approval through the review of the pull request that adds this ADR
- **Supersedes**: none

## Context

The grid is at least 10000×10000 pixels. Each pixel in the current state keeps a color, an author
and an update timestamp. Writes must stay consistent under concurrency, users are rate limited,
and the whole grid must never be one document (C06 §4.3). A Firestore document is limited to
1 MiB, and Google warns about contention on frequently updated documents.

## Options considered

1. **One Firestore document per tile, holding a map of pixels** — one read per tile, but a busy
   zone becomes a hot document and the document grows toward the size limit.
2. **One Firestore document per pixel (sparse)** — no contention, natural per-pixel inspection and
   transactions, but rendering a tile costs up to one read per pixel.
3. **Hybrid: per-pixel documents as the source of truth, tiles as images in Cloud Storage** —
   cheap reads for rendering, more components.

## Decision

Option 3.

- **State**: Firestore, one document per painted pixel, keyed `x:y`, with color, author,
  `updatedAt` and the grid `epoch`. Unpainted pixels have no document.
- **Rendering**: 256×256 tiles stored in Cloud Storage and served through a CDN, regenerated by a
  tile worker from the pixel state. They serve the frontend, `/get` and `/snapshot`. At most about
  40×40 tiles cover 10000×10000.
- **Consistency**: events carry an id for idempotence. Pub/Sub ordering keys use the tile
  coordinates to serialise writes on a tile, and each pixel write is a Firestore transaction that
  keeps the most recent timestamp.
- **Clear**: `/admin clear` increments the grid `epoch`; documents of an older epoch are treated as
  empty, and are deleted later in the background.
- **Rate limit and pause**: one counter document per user and minute, with the admin override in
  its own document; the pause flag lives in a single configuration document.

## Consequences

- Positive: no hot document; cheap rendering; clear is instant; inspecting a pixel is one read.
- Negative / trade-offs accepted: two stores to keep consistent, and a tile worker to write.
  Firestore bills per document write, and the free tier (20,000 writes per day on the Standard
  edition) will be exceeded by a brush load test; check the pricing page before testing.
- Follow-up work: define the tile worker's debounce and the document schema in
  `docs/data-model.md` when the first pixel is stored; exempt unqueried fields from indexing to
  reduce write cost.
